# 카프카 컨슈머 · 파티션 · 리밸런스 전략

> 정산 싱크 컨슈머(`normalize/`)가 카프카를 어떻게 병렬 소비하는지, 그리고 일꾼(컨슈머)이 죽고 살아날 때 무슨 일이 일어나는지 정리한다.
> 학습 목적 문서 — "왜 이렇게 도는가"의 원리를 기록. 실제 설정은 `normalize/src/main/resources/application.yml`.

## 0. 한눈에

| 개념 | 비유 | 정하는 곳 |
|---|---|---|
| **파티션(partition)** | 고속도로 **차선** (토픽을 몇 갈래로 쪼갰나) | 토픽 생성 시 (현재 토픽당 4) |
| **concurrency(스레드)** | 차선을 달리는 **트럭**(일꾼=컨슈머 몇 명) | `application.yml` (현재 8) |
| **리밸런스(rebalance)** | 일꾼들에게 **파티션을 나눠주는 자동 협상** | 카프카 코디네이터(자동) |

> 차선만 많아도 트럭 1대면 1차선씩만 씀. 트럭만 많아도 차선 1개면 줄 섬. **둘 다 늘려야 병렬**이 된다.

---

## 1. 파티션 vs 스레드 — 다른 층위

- **파티션 = 토픽당** 쪼개기 단위 (브로커 쪽). 우리는 토픽당 4.
- **스레드 = 앱이 띄우는 일꾼 수** (앱 쪽). `listener.concurrency`.
- 병렬 처리 **상한 = 그룹이 구독한 전체 파티션 수** (토픽당 4가 아니라 **전 토픽 합산**).

우리 컨슈머는 패턴 `(pay|order)\.public\..*`로 **7개 토픽**을 한 그룹(`normalize-sink`)으로 구독:

```
pay.public.payment / payment_card / payment_money / payment_point / payment_coupon  (5)
order.public.order_item / cancel                                                    (2)
────────────────────────────────────────────────────────────────────────────────────
7토픽 × 4파티션 = 28파티션  → 병렬 상한 = 28
```

| concurrency | 일꾼당 파티션 | 상태 |
|---|---|---|
| 1 | 28개 혼자 | 순차(느림) — 파티션 쪼갠 효과 잠듦 |
| 8 | 약 3~4개씩 | (전략에 따라) 전원 일함 |
| 28 | 1개씩 | 최대 병렬 |
| 40 | 28명 일하고 12명 놀음 | 낭비 |

> **단일 스레드면 파티션을 쪼갠 속도 이득은 없다.** 단 파티션은 "병렬 가능 상한"을 미리 확보해 둔 것 — 나중에 스레드만 늘리면 재파티셔닝 없이 즉시 병렬화. 같은 key는 같은 파티션 → 순서 보장 단위.

## 2. 일감 배정 — 자동, 그리고 "토픽-파티션 단위"

- 일꾼은 떠돌지 않는다. **자기에게 배정된 토픽-파티션 묶음만** 고정 처리(리밸런스 전까지).
- 배정 단위는 토픽 전체가 아니라 **"토픽-파티션 하나하나"** → 한 일꾼이 여러 토픽의 파티션을 섞어 가질 수 있음.
- 누가 뭘 맡을지는 **배분 전략(assignor)** 이 결정 (→ 4장).

### 배정 시점 = 리밸런스
브로커 중 하나가 그룹의 **코디네이터(반장)**. 흐름:
```
① 일꾼들이 join 요청(JoinGroup)  → ② 반장이 리더 일꾼 지정
→ ③ 리더가 전략 돌려 배정 계산   → ④ 반장이 각자에게 통보(SyncGroup)
→ ⑤ 각 일꾼이 자기 파티션 소비 시작
```

---

## 3. 리밸런스 트리거 — "명단/구독" 변화뿐 (일감과 무관)

리밸런스는 **"누가 그룹에 있나 + 무슨 토픽 구독하나"** 가 바뀔 때만 터진다. **LAG(일감) 소진·증가와는 무관.**

| 터짐 ✅ (멤버십·토폴로지 변화) | 안 터짐 ❌ |
|---|---|
| 일꾼 합류(기동·증설·부활) | LAG=0 (일 다 끝남) |
| 일꾼 이탈/사망(종료·크래시·하트비트 끊김) | LAG 산더미(일 넘침) |
| 일꾼 강퇴(`max.poll.interval` 초과 = 처리 너무 느림) | 평소 offset 커밋 |
| 새 토픽 등장(패턴 매칭) | 토픽 비거나 참 |
| 파티션 수 변경 / 코디네이터 교체 | |

> 함정: 일이 너무 많아 처리가 느려지면 "일감 때문"처럼 보이나, 실제 트리거는 **강퇴(=이탈)** 라는 멤버십 변화.

## 4. 배분 전략(assignor) — 설정 가능 ★

`partition.assignment.strategy` 하나가 **"어떻게 나누나" + "eager/cooperative"** 를 동시에 결정.

| 전략 | 배분 | 프로토콜 | 비고 |
|---|---|---|---|
| **RangeAssignor** (현 기본) | 토픽**별로** 따로 | eager(전원 정지) | 토픽당 4 < 일꾼 8이면 **앞 4명만 받고 4명 놀음** ⚠️ |
| RoundRobinAssignor | 전체 파티션 전역 고루 | eager | |
| StickyAssignor | 고루 + 재배분 시 기존 배정 최대 유지(이동↓) | eager | |
| **CooperativeStickyAssignor** | Sticky + **협력적**(옮길 파티션만 멈춤) | **cooperative** | 권장 ✅ |

### RangeAssignor가 8명 중 4명을 놀리는 이유
토픽마다 독립적으로 4파티션을 8명에 range 배분 → 매 토픽이 같은 앞 4명(0~3)에게만 감:
```
payment      4p → 일꾼0,1,2,3 / 4~7 0개
payment_card 4p → 일꾼0,1,2,3 / 4~7 0개   ... 모든 토픽 동일 패턴
→ 일꾼0~3 = 토픽마다 1개씩 7개,  일꾼4~7 = 0개(놀음)
```
RoundRobin/CooperativeSticky는 28개를 전역으로 보고 8명에 3~4개씩 고루 → 전원 일함.

### 설정 방법 (`application.yml`)
```yaml
spring:
  kafka:
    consumer:
      properties:
        partition.assignment.strategy: org.apache.kafka.clients.consumer.CooperativeStickyAssignor
        session.timeout.ms: 45000
        max.poll.interval.ms: 300000
      # group-instance-id: normalize-1   # 정적 멤버십(아래 6장) — 인스턴스마다 유일해야
```
> ⚠️ 그룹 **전원이 같은 전략**이어야 모임. eager↔cooperative 전환은 보통 전체 재시작 필요(섞이면 안 됨).

### 조절 가능한 다른 손잡이
| 손잡이 | 의미 | 기본 |
|---|---|---|
| `session.timeout.ms` | 하트비트 끊겨도 "죽음" 판정까지 대기 | 45s |
| `heartbeat.interval.ms` | 하트비트 주기 | 3s |
| `max.poll.interval.ms` | 한 묶음 처리 최대 허용(넘으면 강퇴) | 5분 |
| `max.poll.records` | 한 묶음 건수(=묶음 무게, 클수록 강퇴 위험↑) | 우리 2000 |

## 5. 리밸런스 타이밍 — 일하는 일꾼은 끊지 않는다

컨슈머는 **`poll()`을 부르는 순간에만** 리밸런스에 참여. 묶음 처리 중(poll 사이)에는 응답 안 함.

예) 일꾼 1~5 중 5 사망, 4는 아직 묶음 처리 중:
```
5 사망 감지 → 리밸런스 시작
1,2,3: poll() 호출 → join 보냄 → 장벽서 대기(멈춤)
4: 2000건 처리 중 → 아직 join 못 함
→ 그룹이 4를 기다림 (1~3은 멈춘 채 = stop-the-world 비용)
4: 처리 끝 → 다음 poll() → 그제야 join → 재배분 확정 → 5의 파티션 분배
```

- **4를 중간에 끊지 않음** — 현재 묶음 끝나고 poll 부를 때 합류.
- **하트비트 vs poll 분리**: 하트비트는 백그라운드 스레드가 보냄 → 4는 처리 중에도 "살아있음" 유지. 하지만 **리밸런스 합류(JoinGroup)는 poll 스레드**에서만 → 처리 끝나야 합류.
- **상한**: 4가 `max.poll.interval.ms`(5분) 넘기면 → "4도 죽음" 판정·강퇴. → `max.poll.records` 너무 키우면 이 위험↑.
- **멈춤 시간 = 가장 느린/바쁜 멤버가 결정** (장벽). 묶음을 가볍게 유지하면 멈춤도 짧아짐. Cooperative면 멈춤 범위가 "옮길 파티션만"으로 축소(단 장벽 자체는 있음).

## 6. 일꾼의 생애주기 — 죽음과 부활

### 죽음 감지
| 죽는 방식 | 감지 기준 |
|---|---|
| 확 죽음(크래시·네트워크 끊김) | `session.timeout.ms`(45s) 안에 하트비트 없으면 사망 |
| 멈춤(살아는 있는데 처리 너무 느림) | `max.poll.interval.ms`(5분) 초과 시 산 채로 강퇴 |

### 죽으면 → 자동 리밸런스로 파티션 재배분
죽은 일꾼의 파티션을 **산 일꾼들이 나눠** 이어받음. 이어받은 일꾼은 **죽은 일꾼이 마지막 커밋한 오프셋부터** 읽음.

### 부활
- **졸다 깨기**: `session.timeout` 안에 하트비트 재개 → 사망 판정도 안 됨, 리밸런스도 없음.
- **재시작**: 다시 join → 리밸런스 → 파티션 재배정(이전과 다를 수 있음) → 커밋 지점부터 밀린 것(LAG) 따라잡음.
- 기본값은 재시작 일꾼을 **새 멤버**로 봄 → 부활마다 전체 리밸런스 1번 더. (롤링 재시작 시 8명×2=16번 출렁)

### 리밸런스 횟수
> 기본: **사망 1번 + 부활 1번 = 2번**. 단 크래시는 사망 리밸런스가 `session.timeout` 뒤 터짐(그 전 부활 시 생략 가능). **정적 멤버십**(`group.instance.id`)을 달면 timeout 내 부활 시 같은 파티션 회수 → 2번 → 0번으로.

## 7. 장애가 심해지면

| 시나리오 | 결과 |
|---|---|
| 일꾼 **전멸**(그룹에 0명) | 아무도 소비 안 함, LAG↑. **단 메시지는 카프카에 보관 → 유실 아님.** 부활하면 따라잡음 |
| **죽음의 소용돌이** | 일부 죽음 → 남은 일꾼 과부하 → `max.poll.interval` 초과 → 연쇄 강퇴 → 전멸 수렴 (원인=용량부족) |
| **리밸런스 폭풍** | 깜빡임(flapping) 반복 → 재배분만 하고 일 못 함 → 처리량 붕괴. **비용의 본질 = 빈도 × 멈춤시간** |
| **브로커 사망** | 운영(브로커 다수·RF≥3): 다른 브로커가 반장 승계 무중단. **우리(브로커 1대·RF=1): 전체 정지** ← 단일노드 한계 실증 |
| **보관기간 초과** | 다운타임 > `retention.ms`(기본 7일)면 **못 읽은 메시지 삭제 = 진짜 유실** (유일한 유실 경계) |

### 리밸런스 비용의 구성
| 항목 | 우리 경우 |
|---|---|
| stop-the-world 멈춤(eager) | 가장 큼 |
| 동기화 장벽(가장 느린 멤버 대기) | 묶음 가벼우면 짧음 |
| 오프셋 커밋 churn(중복 재처리) | dedup이 흡수 |
| **로컬 상태 재구축** | **거의 0** — 우리는 무상태 B방식 |

## 8. 우리 파이프라인이 "죽어도 되는" 이유 — B방식 dedup

카프카 기본 보장 = **at-least-once**(유실 없음, **중복 가능**). 일꾼이 죽어 커밋 못 한 메시지는 부활 후 재처리 → 랜딩에 중복 append.

우리는 이를 **읽기 시점 dedup**으로 흡수:
- 컨슈머는 무상태로 NDJSON에 append만 (중복 신경 안 씀)
- 배치/dbt가 읽을 때 `key별 _seq(=Postgres LSN) 최대 & _op<>'d'`로 1건만 남김
- 같은 메시지는 **같은 key·같은 LSN** → 중복이 자동 제거

> ★ `_seq`는 **반드시 LSN**(카프카 offset 아님). canonical `payment_method`는 4개 토픽(card/money/point/coupon)에서 합류하는데 offset은 토픽마다 독립적으로 셈 → LSN만 DB 전역 단조. (상세 STATUS 3-4)

**결과: 일꾼이 죽고·부활하고·리밸런스가 여러 번 터져도, 순서가 섞여도 → 최종 정산 결과는 비트 동일.** 이것이 무상태 + LSN dedup 설계의 목적.

## 9. 운영 대응 요약

| 위협 | 대응 |
|---|---|
| 일꾼 과부하·전멸 | 오토스케일링(LAG 보고 컨슈머 증설) |
| 죽음의 소용돌이 | `max.poll.records`↓ + 처리 빠르게 → poll 주기 준수 |
| 리밸런스 폭풍 | CooperativeSticky + `session.timeout` 튜닝 + 정적 멤버십 |
| 브로커 사망 | 브로커 3대+ · RF≥3 (우리 1대의 반대) |
| 보관기간 유실 | retention을 최악 다운타임보다 길게 |
