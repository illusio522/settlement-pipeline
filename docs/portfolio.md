# Settlement Pipeline — 파일 기반 일 마감 정산

결제·주문 데이터를 결합해 파트너별 정산 명세를 만드는 프로젝트다. **복합결제·부분취소의 금액 정합성을 유지하고, 같은 입력을 재처리해도 결과가 중복 반영되지 않는 것**을 중심으로 구성했다.

처음에는 CDC·Kafka·레이크하우스 전체 경로를 로컬 Docker로 구현했다. 이후 일 마감 요구에 맞춰 파일 기반 경로를 추가하고, 기존 경로와 동일 원천의 입력·정산 결과를 비교하도록 만들었다. 로컬·개발·운영에 적용할 인프라 설정과 멱등성 설계에는 Claude Code를 활용했다. 구현·검증 환경은 로컬이며 합성 데이터를 사용한다.

| 구분 | 기술 |
|---|---|
| 정산 배치 | Python CLI, Parquet, DuckDB, dbt |
| 원장·게시·조회 | PostgreSQL, Java 21, Spring Boot, Spring Data JPA |
| 실행·검증 | Docker Compose, pytest, JUnit·MockMvc, SQL 전수 비교 |
| 확장 구현 | Debezium, Kafka, Avro, Apicurio, MinIO, Iceberg, Nessie, Spark, Airflow, Prometheus·Grafana |

## 주요 기능과 설계

### 마감 입력을 파일로 고정

일 단위 정산에서는 모든 변경을 실시간으로 운반하기보다 마감 대상 데이터를 확실히 확보하는 것이 중요하다. 결제·주문 DB에서 당일 거래와 계산에 필요한 원결제·상품 정보를 추출하고, Parquet 파일과 manifest로 하나의 입력 묶음을 만들었다.

manifest에는 파일 체크섬·건수·스키마·정산일·상류 마감 명세와 기준정보 버전을 기록한다. 계산 전에 입력을 복사·검증하고, 재시도할 때도 동일한 묶음을 사용한다. 취소의 과거 원결제는 참조 데이터로만 사용해 당일 매출에 중복 합산하지 않는다.

### 복합결제 배분과 금액 대사

결제 금액을 상품가 비율로 라인에 배분하고, 각 라인을 카드·머니·포인트·쿠폰 비율로 다시 나눈다. 반올림 차액을 정해진 마지막 라인·수단에 반영하고, 유효 수수료를 적용해 일자·파트너·브랜드·수단별 정산액을 계산한다.

중복 키, 원거래·주문 누락, 수단 합계 불일치, 수수료 누락, 정산 금액 차이를 검사한다. **검사 실패 시 게시를 중단**해 잘못된 결과가 조회 서비스에 반영되지 않도록 했다.

### 재실행과 동시 게시 제어

입력 명세·계산 코드·정책으로 실행 키를 만들고 PostgreSQL 유일성 제약으로 중복 실행을 제어한다. 완료된 실행은 기존 결과를 반환하고, 실패한 실행은 새 시도로 재개한다. lease와 소유 토큰을 사용해 중단된 작업을 복구하고 이전 실행의 뒤늦은 게시를 막는다.

결과는 전체 테이블을 비우지 않고 해당 날짜만 교체한다. 결과 교체·게시 버전 변경·실행 완료 상태를 하나의 트랜잭션으로 묶고, 기대 게시 버전을 확인해 오래된 계산이 최신 결과를 덮어쓰지 못하도록 했다. 마감 확정과 사유를 기록한 재마감 명령도 제공한다.

### 계산과 조회 분리

DuckDB·dbt는 실행별 파일에서 정산을 수행하고, 검증된 집계만 PostgreSQL에 게시한다. 기존 Spring Boot·JPA API는 API 키 인증과 입력 검증을 적용해 일자별 파트너 요약과 결제수단별 상세를 제공한다.

## 로컬 Docker 구성

기본 경로에서는 인프라를 PostgreSQL과 필요할 때 실행하는 배치 컨테이너로 줄였다. 조회 앱은 호스트에서 실행한다. 파일은 호스트 마운트, DB는 전용 볼륨으로 보관한다.

| 구성 | 역할 |
|---|---|
| PostgreSQL | 결제·주문 DB, 실행 상태·게시 버전·정산 조회 결과 저장 |
| 파일 배치 컨테이너 | 파일 추출·입력 검사·dbt 계산·대사·게시 실행 후 종료 |
| 별도 CDC 검증 스택 | PostgreSQL·Kafka·Debezium·Apicurio로 기존 수집 경로를 재현. 기존 환경과 포트·볼륨 분리 |

## 두 경로의 결과 검증

동일한 원천과 수수료 정책으로 기존 CDC 정산 SQL과 파일 배치 모델을 독립 실행한다. 대상 입력부터 비교하고, 정산 명세·집계의 모든 컬럼을 양방향 `EXCEPT ALL`로 대조해 값 차이와 행 중복을 검출한다. 불일치는 실패 코드와 비교 보고서로 남긴다.

테스트에는 반올림 경계, 과거 결제의 당일 취소, 기존 생성기 1,000주문 회귀, 입력 위변조·누락, 중복 실행, lease 만료, 게시 롤백·버전 충돌을 포함했다. 실제 PostgreSQL 통합 테스트와 기존 Java 테스트도 함께 실행한다. 재현 절차와 검증 결과는 [파일 배치 가이드](FILE-BATCH.md)와 [검증 결과](FILE-BATCH-VERIFICATION.md)에 정리했다.

## 요구 확대에 대비한 기존 확장 구현

| 확장 요구 | 구현·검증한 내용 |
|---|---|
| 실시간 변경 수집 | Debezium·Kafka와 Java 정규화 컨슈머, Avro 스키마 처리, DLT 격리 |
| 수집 병렬화 | 파티션·컨슈머 배정 전략 조정. 기존 동일 조건 실험에서 5.88초→3.07초, 약 1.9배 개선 |
| 레이크하우스·엔진 교체 | MinIO·Iceberg·Nessie와 Spark 정산 경로를 구성하고 DuckDB 결과와 비교 |
| 배치 운영·관측 | Airflow DAG, Prometheus·Grafana의 lag·처리량·파티션 배정 대시보드 |

확장 경로는 기본 파일 배치의 필수 의존성으로 두지 않았다. 현재 범위는 로컬 정산 계산·게시이며, 실제 PG 독립 대사·송금과 운영 고가용성은 후속 영역이다.
