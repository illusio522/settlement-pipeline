# Settlement Pipeline — 파트너 정산 데이터 파이프라인

결제·주문 데이터를 수집해 파트너별 정산 명세와 일별 집계를 만드는 Java/Spring·SQL 기반 프로젝트다. **복합결제와 부분취소를 반영하면서 금액 정합성을 유지하고, 재처리해도 같은 결과를 만드는 것**을 중심으로 설계했다.

로컬 Docker 환경에서 CDC 수집부터 정규화, 레이크 저장, 정산·대사, 배치 실행, 조회 API까지 구현했다. 개발 과정에서 **로컬·개발·운영 환경에 적용할 수 있는 인프라 설정과 정합성을 위한 멱등성 설계에 Claude Code를 활용했다.** 실제 구현·검증 환경은 로컬이며 합성 데이터를 사용했다.

| 구분 | 기술 |
|---|---|
| 애플리케이션 | Java 21, Spring Boot 3.3.5, Spring Kafka, Spring Data JPA |
| 수집·저장 | PostgreSQL, Debezium, Kafka, Avro, Apicurio Registry, MinIO, Iceberg |
| 정산·실행 | DuckDB, dbt, Spark, Nessie, Airflow, Docker Compose |
| 검증·관측 | JUnit 5, MockMvc, dbt 테스트, Prometheus, Grafana |

## 주요 기능과 설계

### 결제·주문 데이터 수집과 정규화

결제 원장에는 거래 총액과 결제수단이 있고, 판매 파트너 정보는 주문 상품에 있다. 두 도메인을 결합해야 파트너별 정산이 가능하므로 결제·주문 DB에 각각 Debezium 커넥터를 연결하고, 변경 이벤트를 Kafka로 수집했다.

Spring Kafka 컨슈머는 카드·머니·포인트·쿠폰 원장을 하나의 `payment_method`로 통합한다. 정산에 필요한 필드만 남겨 **소스 7개 테이블을 공통 모델 4개로 변환**하고, 배치가 원본 테이블 구조에 직접 의존하지 않도록 했다. Avro와 Schema Registry로 메시지 스키마를 관리하고, 처리할 수 없는 이벤트는 DLT로 격리한다.

### 복합결제·부분취소 정산과 금액 보존

한 주문에 여러 파트너와 결제수단이 섞이면 단순 합산만으로는 각 파트너의 정산액을 구할 수 없다. 거래 금액을 상품가 비율로 주문 라인에 배분한 뒤, 각 라인을 원결제 수단 비율로 다시 나눴다.

배분 과정의 반올림 차이는 마지막 라인과 결제수단에 반영해 합계가 원금과 같도록 했다. 부분취소는 취소 대상 라인만 계산하고, 정산일에 유효한 수수료율을 적용해 **정산일·파트너·브랜드·결제수단별 집계**를 만든다. 결제 총액과 정산 집계의 차이를 대사해 금액 보존을 확인한다.

### 재처리를 위한 멱등성과 증분 처리

CDC 이벤트는 재수신될 수 있고 배치도 재실행될 수 있다. 수집 단계에서는 이벤트를 파일에 추가하고, 읽을 때 키별 최신 이벤트를 선택하도록 구성해 중복 수신이 정산 결과에 중복 반영되지 않도록 했다.

초기에는 Kafka offset을 증분 처리 기준으로 사용했지만, 여러 결제수단 토픽을 합칠 때 토픽마다 다른 offset 때문에 누락이 발생했다. 이를 PostgreSQL의 변경 위치인 **LSN 기반 `_seq`**로 바꾸고, dbt staging 4개 모델에 watermark와 키별 `delete+insert`를 적용했다. 삭제 이벤트도 반영하며, 정산 중간 모델과 마트는 전체 재생성한다.

고정 원장의 정산 재실행과 증분 결과 비교로 멱등성을 검증했다. 적용 범위는 읽기 중복 제거와 배치 결과의 멱등성이며, 전체 수집 경로의 exactly-once 전달을 보장하는 구조는 아니다.

### 레이크 저장과 처리 엔진 분리

수집 컨슈머가 정산 DB를 직접 갱신하면 수집과 배치의 쓰기가 충돌할 수 있다. 이를 피하기 위해 이벤트를 테이블·Kafka 파티션별 NDJSON 파일에 저장하고, 배치가 읽어 MinIO의 Parquet·Iceberg로 적재하도록 분리했다.

DuckDB SQL로 정산 로직을 먼저 검증하고, dbt로 모델 의존성과 데이터 테스트를 관리했다. 별도로 Spark·Nessie 기반 Bronze·Silver·Gold 경로를 구현해, **처리 엔진이 바뀌어도 같은 정산 결과를 만드는지** 기준 데이터와 비교했다. Spark 경로는 로컬에서 검증했으며 다중 노드 성능 검증은 포함하지 않는다.

### 배치 실행과 정산 조회 분리

정산 실행 순서와 재시도를 관리하기 위해 Airflow에 Parquet 적재, Iceberg 생성, 정산·대사, 서빙 DB 게시의 4단계 DAG를 구성했다. Parquet와 Iceberg 생성은 각각 로컬 랜딩 파일을 읽는다.

조회 요청이 DuckDB 배치 작업과 충돌하지 않도록 결과를 PostgreSQL `servedb`에 게시한다. `TRUNCATE + COPY`를 트랜잭션으로 묶어 재적재하고, 원본과 대상의 행 수를 비교한다. Spring Boot·JPA API는 API 키 인증과 입력 검증을 적용해 일자별 파트너 요약 및 결제수단별 상세를 제공한다.

## 로컬 Docker 구성

인프라는 Docker Compose로 구성하고, 연산 컨테이너는 필요할 때 실행하도록 분리했다. 구성 요소별 역할은 다음과 같다.

| 구성 요소 | 역할·구성 이유 |
|---|---|
| PostgreSQL | 결제·주문 DB를 논리적으로 분리하고, 정산 조회와 Airflow 메타데이터 저장소로 사용 |
| Kafka | 변경 이벤트를 보관하고 수집·처리 속도 차이를 흡수. 로컬에서는 KRaft 단일 노드로 구성 |
| Debezium / Kafka Connect | 결제·주문 DB의 WAL 변경을 Kafka에 전달 |
| Apicurio Registry | Avro 스키마를 등록·조회해 생산자와 소비자의 메시지 구조 공유 |
| MinIO | Parquet·Iceberg를 저장하는 S3 호환 레이크 |
| Nessie | Spark 경로의 Iceberg 카탈로그 관리 |
| Airflow | 정산 작업의 실행 순서와 실패 재시도 관리 |
| Kafka UI | 토픽·메시지·컨슈머와 커넥터 상태 확인 |
| Kafka Exporter | 컨슈머 지연·오프셋 메트릭 노출 |
| Prometheus | Kafka 및 Java 앱의 처리량·지연·JVM 메트릭 수집 |
| Grafana | 메트릭과 컨슈머별 파티션 배정을 대시보드로 확인 |
| DuckDB·dbt·Spark | `docker run --rm`으로 배치 실행 후 종료해 상시 연산 자원 사용을 줄임 |

Java 컨슈머와 조회 API는 호스트에서 실행한다. 주요 저장소는 Docker 볼륨으로 보존하고 자격증명은 환경변수로 분리했다. Kafka 단일 노드와 Nessie 인메모리 카탈로그 등은 로컬 검증용 구성이다.

## 성능 개선과 검증

**전체 처리 경로를 측정해 수집 병목을 먼저 개선했다.** 초기 10만 주문 실험에서 컨슈머 랜딩이 전체 시간의 약 90%를 차지해 파티션 수, 컨슈머 병렬도, 배정 전략을 조정했다. 동일 입력과 poll 설정으로 비교한 결과, 단일 컨슈머 5.88초에서 CooperativeSticky 기반 8개 컨슈머 3.07초로 약 1.9배 개선됐다.

이후 파일 쓰기 락이 병목이라는 가설로 파티션별 샤딩을 적용했지만 3.07초에서 2.96초로 변화가 작았다. 해당 가설을 철회하고 추가 병목 분석 과제로 남겼다.

| 검증 항목 | 내용 |
|---|---|
| 정산 성능 | Docker 10 vCPU·31.5GiB 환경에서 1,000만 주문, 약 5,116만 정산 이벤트를 DuckDB로 57초에 처리. CDC 수집 제외 |
| 데이터 정합성 | CDC·레이크 경로의 소스 4종과 정산 집계 체크섬을 기준 데이터와 비교 |
| 멱등성 | 고정 원장 재정산 결과 일치, dbt 무변경 재실행과 UPDATE 반영 확인 |
| Java 테스트 | CDC 파서 13개, MockMvc 기반 API 테스트 7개, 결제수단 매핑 1개 |
| dbt 테스트 | 키 유일성·필수값·허용값·참조 무결성 검사 15개 |

성능과 E2E 결과는 [기존 실험 기록](BENCHMARK.md)과 [검증 기록](STATUS.md)을 기준으로 하며 이번 문서 작성 시 재실행하지 않았다. PG 대사는 합성 원장에서 만든 모의 데이터를 사용한다. 실제 환불·송금, 대사 실패 시 게시 차단, 운영 고가용성 구성은 구현 범위에 포함하지 않는다.
