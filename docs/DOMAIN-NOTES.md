# 도메인 메모 (사용자 확인 사항)

> 정길훈 님이 설계 과정에서 확인·정리한 도메인 이해. 구현·검증 시 이 기준을 따른다.

## 1. brand = 몰(플랫폼)
- `brand` = 결제가 일어난 **몰** (몰A / 몰B)
- 코드값: `1=mall-a(몰A)`, `2=mall-b(몰B)`
- brand는 **결제 데이터(MID)로 알 수 있다** (어느 몰에서 결제됐나)

## 2. MID 구조 — payments_mid ↔ pg_mid ↔ brand
- `payments_mid` = **자체 페이먼츠(인하우스)가 가맹점(몰)에 발급한 MID**. 결제 원장에 박혀 있음.
- 이 페이먼츠 MID는 **그 브랜드가 쓰는 PG사 MID(`pg_mid`)와 매핑**된다 (자체 페이먼츠(인하우스)가 외부 PG/카드사 연동 시 쓰는 가맹점 ID).
- 매핑: `payments_mid → pg_mid → brand`
- ★ **브랜드당 MID는 2개 이상**으로 모델링한다 (1:1 아님). 현실에서 한 브랜드가 PG사별 / 결제수단별 / 사업자(법인)별 / 정산주기별로 여러 MID를 가짐.
- 따라서 `brand 1개 → payments_mid 여러 개 → 각 pg_mid` (다대일).

## 3. partner = 입점업체(셀러) — 결제 원장에 없음
- `partner` = 그 몰에 입점한 셀러 (정산 대상)
- ★ **결제 원장엔 partner가 없다.** 결제는 MID(몰)·총액까지만 안다.
- partner는 **주문상품(order_item)에서 등장** → `order_no`로 결제와 조인해 귀속.
- 정산 = 결제(돈) ⋈ 주문(귀속) 두 도메인을 잇는 일.

## 4. 복합결제 (복수 결제수단) ★ v3
- 한 주문을 **여러 결제수단으로 동시 결제**. 구조 = `payment`(헤더, 주문 총액) + `payment_method`(수단별 N행).
- **주결제수단(MAIN)**: 신용카드(CARD)·머니(MONEY). PG·MID 대사 대상(`is_pg=TRUE`).
  - 주결제수단은 **동시 사용 가능**(카드+머니 분할결제).
  - **확대 용이**가 조건 → `method_type` 마스터에 행 추가만으로 확장(예: BANK). 정산 로직 불변.
- **보조결제수단(AUX)**: 포인트(POINT)·쿠폰(COUPON). **플랫폼 부담(수수료 0)**, PG 대사 대상 아님(MID NULL). 정산 명세엔 표기.

## 5. 차등 수수료 & 결제수단별 백데이터 ★ v3
- **셀러 정산 지급액 = 상품가(item) 기준 총액** (결제수단 무관, 돈은 합산해 지급).
- 단 **백데이터·수수료는 결제수단별**로 제공 → `settlement_event`(라인×수단) → `settlement_agg`(파트너×수단).
- **결제수단별 차등 수수료**: `method_fee`(버전드, as-of). 카드 2.5%(2026-06-01부터 2.3%)·머니 1.5%·포인트/쿠폰 0%.
- **거래시점 수수료 박제(freeze)**: 거래일 기준 as-of 수수료를 settlement_event에 불변 저장 → 재현·감사.

## 6. 정산 ≠ 환불 ★ 범위 확정
- **정산**: 결제·주문 → 파트너 지급액. **취소는 셀러 정산에서 차감까지만** 다룸(`cancel` 라인 명세, 부분취소 포함).
- **환불(자금 환불 정책·환불 대사, 원결제와 다른 수단으로의 환급 등) = 정산 범위 밖** → 본 파이프라인 미구현. 별도 자금 도메인.

## 7. 1단계(DuckDB) 구현 단순화 (테스트용)
- brand 2개(몰A·몰B), partner 100개(1~50=몰A, 51~100=몰B 입점사)
- partner_id=1(mall-a-main) = 몰A 70% 스큐 핫파트너
- **브랜드당 MID 2개 이상**으로 시드 (카드 몰A→1001·1003, 몰B→1002·1004 / 머니 몰A→1101, 몰B→1102).
- `mid_map`은 현재 `(payments_mid, brand)` — `pg_mid`는 PG 3자대사 붙일 때 추가 예정.
- 전부 **합성 데이터** (실데이터 아님), 구조·로직 검증용.
- 시드는 **결정적(재현 가능)** — `random()` 비결정 차단(hash 배정 + 단일스레드). 자세히는 DATA-LAYOUT §6.

## 8. 대사(Reconciliation) 단위 ★ v3 (2종 구현)
- PG는 **MID(가맹점) 단위로 정산** → MID 대사는 주결제수단(카드·머니) MID별.
- **대사① 파트너 돈 보존**(`recon_result`): 결제원천 PAY 합 = 내부 집계 gross 합 (diff=0).
- **대사② 주결제수단 MID 대사**(`recon_card`): 내부 결제수단 합(MID별) = PG 정산파일(`pg_settlement_file`) (diff=0).
- 보조결제(포인트·쿠폰)는 PG 대사 대상 아님.
