# 4-A 성능 측정 — 단일 노드(DuckDB) 규모별 벤치

> 목적: **인프라 변경 없이**(DuckDB 단일 노드) 데이터를 키워 처리시간·병목·안정성 실측.
> 환경: Docker, 10 vCPU / 31.5GiB. 이미지 `settlement-duckdb:1.5.3`.
> 측정: canonical 데이터 직접 생성(CDC 미경유) → `03_settlement.sql` 정산 → 단계별 wall-clock.
> 스크립트: `bench/bench_seed.sql`(규모 파라미터), `bench/run-bench.sh`.

---

## 결과

| 주문 수 | 생성(s) | 정산(s) | settlement_event | 정산 처리량(ev/s) | settlement_agg |
|---:|---:|---:|---:|---:|---:|
| 100,000 | 1.1 | 1.7 | 510,918 | ~300,000 | 9,994 |
| 1,000,000 | 4.0 | 5.6 | 5,113,765 | ~913,000 | 10,000 |
| 10,000,000 | 37 | 57 | 51,159,331 | ~898,000 | ~10,000 |

> 10M은 안정화 설정(`SET threads TO 6; SET memory_limit='24GB'`) 적용. 100k·1M은 기본.

## 스케일링 해석

```
정산 시간:  1.7s → 5.6s → 57s   (데이터 10배씩)
  100k→1M : 3.3배 (10배 데이터) → 선형 이하 ✅ (고정비 분산)
  1M→10M  : 10.2배 → 거의 선형 (대량 구간 = 데이터 비례)
처리량:    30만 → 91만 → 90만 ev/s → 약 90만 ev/s에서 안정(plateau)
```

- **컬럼나·벡터화 엔진**이라 소규모는 고정비 때문에 처리량이 낮고, 규모가 커지면 ~90만 ev/s로 수렴.
- 1000만 주문(5천만 이벤트) 정산 = **57초** (단일 노드).
- 정산 결과 행수(agg)는 규모와 무관하게 ~1만 (파트너 100 × 날짜 × 브랜드 × 결제수단) — 집계는 항상 작게 유지.

## 1억 외삽 (참고)

| 가정 | 정산 시간(외삽) |
|---|---|
| 1억 **주문** (≈5억 이벤트) | ~570s ≈ **9.5분** |
| 1억 **이벤트** (≈2천만 주문) | ~110s ≈ **2분** |

→ 단일 노드 DuckDB도 **1억 규모를 단일~10분대**에 처리. 일 1회 정산 배치 윈도우엔 충분. (단, 아래 안정성·운영 한계 참고)

## ★ 크래시 분석 (중요)

### 증상
첫 벤치 루프에서 100k 성공 후 **1M 구간에서 `exit 139`로 죽음.** 단, 1M 단독 실행은 성공.

### 원인
| 단서 | 해석 |
|---|---|
| exit 139 = 128+11 = **SIGSEGV** | 메모리 부족(137)이 아닌 **DuckDB 내부 세그폴트** |
| 단독 성공 / 루프 크래시 = 비결정적 | **경쟁조건(race condition)** |
| 윈도우 함수 대량 병렬 | 1단계서 본 `unordered_map::at`와 동일 계열 |

→ **DuckDB 1.5.3이 대량 데이터 + 풀 병렬(스레드 10) + 윈도우 연산이 겹칠 때 간헐적 세그폴트.** 메모리 한도 미설정 시 자료구조 폭주.

### 해결
| 설정 | 효과 |
|---|---|
| `SET threads TO 6` (10→6, **줄임**) | 동시 메모리 접근 ↓ → 경쟁조건 완화 |
| `SET memory_limit='24GB'` | 한도 초과 시 **디스크 스필**(크래시 대신 느려짐) |

→ 10M이 이 설정으로 크래시 없이 57초 완주. **속도 거의 손해 없이 안정성 확보** (속도↔안정 트레이드오프).

> 교훈: "병렬은 많을수록 빠르다"는 대량서 틀림. **너무 많은 병렬 → 경쟁·메모리 압박 → 불안정.** 적정 병렬 + 자원 한도가 안정의 핵심.

## 운영 관점 — 단일 노드의 한계 (4-B로 가는 이유)

이 튜닝은 **분석 엔진(DuckDB) 한정**이며, 운영 트랜잭션 DB(Postgres)와 무관. 그리고 더 본질적으로:

| 단일 노드 DuckDB | 한계 |
|---|---|
| 안정성 | 대량서 **수동 튜닝 필요·세그폴트** 위험 |
| 가용성 | 단일 노드 장애 = 전체 중단 |
| 확장성 | 한 머신 자원 한도 (수직 확장만) |
| 장애 복구 | 쿼리 실패 시 **전체 재실행** |

→ 운영 대량 정산은 **분산 엔진(Spark/Trino/Snowflake)**:
- 익스큐터/메모리 자동 스케줄링 (수동 SET 불필요)
- 태스크 단위 **재시도**(전체 재실행 아님)
- 노드 추가로 **수평 확장**
- 메모리 부족 자동 스필

**4-A 결론**: 단일 노드는 1000만까진 빠르나(57초), 대량서 자원 수동제어·불안정 → **운영은 분산(4-B)이 필요**함을 실측으로 확인.

# 4-A(E2E) — 전 구간 단계별 측정

> 4-A가 "정산 엔진만" 격리했다면, 이건 **수집 경로 전체**(Postgres→CDC→Kafka→컨슈머→랜딩→정산)를
> 거치며 **단계별 시간·병목**을 측정. 100k 주문 = 약 58만 CDC 메시지.

## 결과 (100k 주문, 58만 메시지)

| 단계 | 시간 | 비중 | 처리량 |
|---|---:|---:|---|
| ① PG 적재 | 6s | 6% | ~10만 행/s |
| ② CDC→Kafka 전파 | 1s | 1% | 로그테일링(즉시) |
| ③ **컨슈머 랜딩** | **96s** | **90%** | **6,042 msg/s** |
| ④ 정산(DuckDB) | 3s | 3% | ~17만 ev/s |
| **합계** | **106s** | | |

> 결과 검증: settlement_agg 체크섬 = 1단계 정답지 동일(`10266430619052066961`).

## ★ 핵심 발견 — 병목은 컴퓨트가 아니라 "컨슈머(수집)"

```
4-A(엔진만) 정산 = 3s (3%)
E2E 병목     = 컨슈머 랜딩 96s (90%)
```
- **정산 엔진을 최적화해도 E2E는 안 빨라짐** — 컨슈머가 90% 차지.
- "엔진만 측정"과 "전 구간 측정"을 둘 다 해야 진짜 병목이 보인다는 교훈.

## 컨슈머 병목 원인 & 개선책

| 원인 | 개선책 |
|---|---|
| 토픽 1파티션 → 단일 `@KafkaListener` 순차 | **파티션 늘리고 컨슈머 concurrency↑** (병렬 소비) |
| 메시지 건당 파싱·정규화·파일쓰기 | **배치 리스너**(N건 모아 처리) |
| `synchronized` LandingWriter(직렬화) | 테이블별 writer 분리 / 비동기 버퍼 |
| JSON 역직렬화 비용 | Avro 등 바이너리(스키마 레지스트리) |

→ 운영에선 **파티션 N개 + 컨슈머 N개 병렬**이 표준. 단일 컨슈머 6천 msg/s → 파티션·인스턴스 늘려 선형 확장.

## 종합 결론

- **컴퓨트(DuckDB 정산)는 충분히 빠르다**(58만 이벤트 3초). 병목 아님.
- **수집(컨슈머)이 E2E 병목** — 파티션·병렬 컨슈머로 확장해야.
- 즉 "정산 시스템 성능"은 엔진이 아니라 **수집 파이프라인의 병렬도**가 좌우.
- 4-B(분산)에서 컴퓨트를 Spark로 키우기 전에, 실제론 **컨슈머 병렬화**가 더 시급한 개선임을 실측으로 확인.

# 4-A(병렬화) — 컨슈머 병목 개선

> 병목(컨슈머 96s)을 병렬화로 개선. 3가지 동시 적용.

## 적용한 것
1. **토픽 파티션 1 → 4** (7토픽 재생성, CDC가 key 해시로 균등 분산 — order_item 파티션별 ~75k)
2. **컨슈머 concurrency=8** (`application.yml`, 스레드 8개 병렬 소비) + `max-poll-records=2000`
3. **LandingWriter 테이블별 락** (전역 synchronized → holder별 lock, 직렬화는 락 밖 → 다른 테이블 동시 쓰기)

## 첫 측정의 "70배"는 폐기 (과장)
첫 측정은 단일 96s → 병렬 1.37s = **70배**로 보고됐으나 **과장이라 폐기**:
① 병렬 1.37s는 "소비/오프셋 커밋"만 잰 것(flush 전) ② 비교 불공정(단일 max-poll 500·전역락 vs 병렬 2000·테이블별락) ③ 단일 96s 자체가 옛 설정(max-poll 500+전역락+verbose)으로 느렸던 값.
→ 아래 **공정 재측정**으로 대체.

# 4-A(병렬화) 공정 재측정 — 전체 여정 S0→S3 (2026-06-19)

> 공정 원칙: ①양쪽 동일 max-poll=2000 ②동일 입력(매 런 오프셋 earliest 리셋→같은 58만건 재소비) ③종료판정 = **랜딩 줄 수 plateau**(flush 포함, LAG 안 봄), 마지막 증가시각 기준. 스크립트 `scripts/consumer-bench.sh`.
> 입력: 58만 메시지(order_item 30만=52% · payment_method 16.5만 · payment 10.5만 · cancel 0.99만), 7토픽×4=28파티션.

## 결과

| 단계 | 파티션 | conc | 전략 | 적재시간(work) | 일꾼 배정 | 의미 |
|---|---|---|---|---:|---|---|
| **S0** (과거 문서값) | 1 | 1 | — | **96s** | 1명 | 옛 baseline(max-poll 500+전역락, 불공정) |
| **S1=M1** 단일(재측정) | 4 | 1 | — | **5.88s** | 1명이 28파티션 | 깨끗한 단일 baseline |
| **S2=M2** 병렬·기본전략 | 4 | 8 | RangeAssignor | **3.65s** | **8명 중 4명만**(각 7p), 4명 놀음 | 전략이 절반 놀림 |
| **S3=M3** 병렬·전략수정 | 4 | 8 | CooperativeSticky | **3.07s** | **8명 전원**(각 3~4p) | 전원 일함, 천장 도달 |

> 셋 다 최종 flush 후 정확히 580,069줄 도달(공정성 확인). plateau ~579,734(버퍼 꼬리 ~335줄, 동일).

## 발견 1 — 배분 전략이 일꾼 절반을 놀린다 (`--describe` 실측)
```
M2 RangeAssignor:  sink-1,2,3,4 = 7파티션씩 / sink-5,6,7,8 = 0파티션(놀음)
M3 CoopSticky:     sink-1~8 = 3~4파티션씩 (전원 일함)
```
→ **concurrency=8 설정만으론 부족.** 기본 RangeAssignor는 토픽별 배분이라 토픽당 4파티션 < 일꾼 8 → 앞 4명만 받음. **CooperativeSticky로 바꿔야 8명 전원** 가동. (상세 `KAFKA-CONSUMER.md` 4장)

## 발견 2 — "70배"의 진실: 실제 병렬 효과는 ~1.9배
```
공정 비교(동일 설정, conc만 1→8):  5.88s → 3.07s = 1.9배
96s→3.07s = 31배는 대부분 설정 개선(max-poll·락·로그) 덕, 스레드 병렬 덕이 아님.
```
단일 스레드가 이미 ~9.9만 건/s로 빠름. 옛 96초는 "단일이라서"가 아니라 옛 설정 탓.

## 발견 3 — 1.9배에서 멈춘 이유: 병목이 컨슈머→쓰기로 이동
랜딩 쓰기는 **테이블별 락**. order_item이 전체 52%(30만)인데 **단일 락으로 직렬화** → 컨슈머를 늘려도 이 테이블은 못 쪼갬.
```
단일 처리율 = 580,069 / 5.88s ≈ 98,650건/s
order_item 직렬 하한 = 300,000 / 98,650 ≈ 3.04s
M3 실측 적재시간      = 3.07s   ← 거의 정확히 일치 → 병목 = 가장 큰 테이블의 직렬 쓰기
```
"쓰기 시점" = `LandingWriter.write`의 `synchronized(h){ h.writer.write(json) }` (테이블 락 안 append). 파싱·정규화·직렬화는 락 밖 병렬, **append만 테이블당 직렬.**

## 결론
- 병렬화 효과는 **실측 ~1.9배** (70배·8배 아님). 정직한 수치.
- **3가지를 함께** 풀어야: 파티션(일감분할)·concurrency(처리병렬)·**전략(CoopSticky로 전원가동)**. 하나라도 막히면 병렬 무효 — 특히 **전략을 안 바꾸면 절반이 논다.**
- 8/8 전원 가동해도 **쓰기 천장**(order_item 단일락 ~3.0s)에서 막힘 → 다음 개선은 컨슈머 증설이 아니라 **order_item 쓰기 샤딩**(파티션별 파일 분할)·배치 쓰기. 단일노드 병렬화의 구조적 한계 = 4-B 분산으로 가는 근거.
- 우리 설계가 멱등·`_seq`(LSN) dedup이라 순서 무관 → 병렬·재처리 안전(측정 중 매 런 재소비해도 결과 동일).
