# 파일 배치 성능 측정과 CDC 비교

`feat/file-batch`의 파일 기반 정산을 규모별로 실행해 단계별 소요 시간을 재고, 같은 조건에서 기존 CDC 경로와 비교한 기록이다. 두 경로의 처리 한계와 병목을 확인하려는 개발자와 포트폴리오 검토자를 위한 문서다.

파일 배치는 2026-11-02, CDC는 2026-11-03에 같은 머신에서 측정했다. 로컬 합성 데이터로 측정했으며, 운영 환경 성능을 보장하는 결과가 아니다.

## 결론

- 파일 배치는 하루 거래 550만 건(전체 주문 1,000만)을 추출부터 게시까지 **158초**에 처리했다. 이 과정에서 정산 명세 2,640만 행을 계산했다.
- 같은 조건의 100만 주문에서 마감 기준 전체 소요는 **파일 배치 18.07초, CDC 189.89초**다. 파일 배치가 10.5배 빠르다.
- CDC 시간의 95%는 PostgreSQL에서 랜딩까지 옮기는 운반이다. 운반 이후 단계(랜딩 적재·정산·게시)만 보면 CDC가 6.46초로, 파일 배치의 정산·게시 9.48초보다 짧다.
- 따라서 일 마감 정산에는 파일 배치가 적합하다. CDC는 운반이 하루 동안 나뉘어 일어나고 장중 실시간 현황이 필요할 때 마감 후 지연을 줄인다. 대신 Kafka·Connect·Registry·컨슈머를 상시 운영하고 저장 공간을 약 60배 쓴다.
- 파일 배치의 병목은 **추출 단계**다. 1,000만 주문에서 전체의 77%를 차지하고, 100만→1,000만 구간에서 데이터는 10배, 시간은 14.2배 늘었다.
- 같은 bundle을 다시 실행하면 0.02초 이내에 기존 실행 결과를 반환한다. 모든 규모에서 중복 게시는 없었다.

## 파일 배치 규모별 결과

| 전체 주문 | 대상일 거래 | 정산 명세 행 | 추출(s) | 정산·게시(s) | 합계(s) | 처리량(거래/s) |
|---:|---:|---:|---:|---:|---:|---:|
| 100,000 | 55,212 | 265,582 | 0.82 | 4.40 | 5.22 | 10,577 |
| 1,000,000 | 549,099 | 2,636,266 | 8.53 | 9.48 | 18.07 | 30,388 |
| 10,000,000 | 5,500,697 | 26,403,049 | 121.24 | 37.22 | 158.46 | 34,713 |

- 10만·100만 주문은 3회 측정의 중앙값이다. 3회 합계의 편차는 10만 주문 5.14~5.46초, 100만 주문 17.50~18.70초다.
- 1,000만 주문은 1회만 측정했다. 편차는 확인하지 않았다.
- 대상일 거래는 대상일의 결제와 취소를 합한 건수다. 처리량은 이 건수를 합계 시간으로 나눈 값이다.
- 모든 실행에서 입력 검사 41개와 결과 검사 5개를 통과했고, revision 1로 게시됐다.

### 단계별 소요 시간

| 단계 | 하는 일 | 10만(s) | 100만(s) | 1,000만(s) |
|---|---|---:|---:|---:|
| `export` | PostgreSQL 2개 DB에서 대상일·원결제·주문 데이터를 Parquet bundle로 추출 | 0.82 | 8.53 | 121.24 |
| `snapshot` | bundle을 실행 디렉터리로 복사하고 체크섬·스키마 검사 | 0.02 | 0.13 | 3.86 |
| `load_inputs` | Parquet을 DuckDB 원천 테이블로 적재 | 0.05 | 0.37 | 3.39 |
| `input_checks` | 입력 검사 41개(중복·참조·금액·통제 합계) | 0.07 | 0.47 | 5.58 |
| `dbt_build` | dbt 모델로 배분·수수료·집계 계산 | 0.80 | 4.14 | 18.03 |
| `compute_other` | dbt 프로세스 기동, 결과 Parquet 기록 등 | 3.37 | 4.08 | 5.89 |
| `output_checks` | 결과 검사 5개(금액 보존·지급식·정산일) | 0.01 | 0.04 | 0.38 |
| `claim`·`stage`·`publish` | 실행 소유권 획득, 게시 후보 적재·대조, 날짜 단위 교체 | 0.05 | 0.07 | 0.08 |

- 정산 단계는 100만→1,000만 구간에서 3.9배만 늘었다. dbt 프로세스 기동 등 약 3.5초의 고정 비용이 있어서 소규모에서는 이 비용이 대부분을 차지한다.
- 게시 비용은 규모와 거의 무관하다(0.08초 이하). 게시 대상인 일자별 집계가 400행으로 고정되기 때문이다.
- 1,000만 주문에서 가장 느린 dbt 모델은 `int_priced`(5.7초)다. 수수료 기간을 `ASOF JOIN`으로 붙이는 단계다.
- 1,000만 주문에서 가장 느린 입력 검사는 `order_item:unique`(0.95초)다. 41개 검사 중 1초를 넘는 것은 없다.
- dbt 하위 프로세스의 최대 메모리는 규모별로 394MB, 1,263MB, 3,756MB다.

## CDC 경로와 비교

CDC 경로는 PostgreSQL → Debezium(Avro) → Kafka → 기존 Java 컨슈머 → NDJSON 랜딩 → 기존 `e2e_load.sql` → 기존 `03_settlement.sql` → servedb 게시 순으로 실행했다. 기존 업무 SQL과 Java 코드는 수정하지 않았다.

### 비교 조건

| 구분 | 내용 |
|---|---|
| 같게 맞춘 것 | 머신, 원천 데이터(`bench_seed.sql`), 규모, 날짜 분포, PostgreSQL 이미지와 설정, DuckDB 스레드 2개 |
| 측정에서 뺀 것 | 합성 데이터 생성과 원천 DB 적재(양쪽 동일) |
| 운반 범위 | 파일 배치는 대상일 범위만 추출한다. CDC는 테이블 전체를 운반한다(100만 주문에서 318만 행 대 580만 레코드) |
| 정산 범위 | 기존 `03_settlement.sql`은 랜딩의 모든 날짜를 정산한다. 이번 데이터에서는 2일치다 |
| 운반 방식 | 초기 snapshot으로 한 번에 운반했다. 하루 동안 나눠 운반하는 운영 방식보다 CDC에 불리하다 |
| 커넥터 등록 | Apicurio 2.4.1의 동시 스키마 등록 오류를 피하려고 결제 → 주문 순서로 등록했다 |
| Docker 메모리 | 약 3.8GiB를 파일 배치는 PostgreSQL 하나가, CDC는 PostgreSQL·Kafka·Connect·Apicurio 4개가 나눠 쓴다 |

### 결과

| 전체 주문 | 대상일 거래 | 정산 명세 행 | 운반(s) | 정산·게시(s) | 합계(s) | 배치 합계(s) | CDC / 배치 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 100,000 | 55,214 | 512,318 (대상일 265,601) | 42.21 | 1.00 | 43.18 | 5.22 | 8.3배 |
| 1,000,000 | 549,159 | 5,117,586 (대상일 2,635,572) | 183.38 | 6.46 | 189.89 | 18.07 | 10.5배 |

- 3회 측정의 중앙값이다. 3회 합계의 편차는 10만 주문 42.36~43.55초, 100만 주문 189.24~192.95초다.
- 운반은 커넥터 등록부터 컨슈머 정상 종료(버퍼 flush)까지다. 정산·게시는 랜딩 적재, 기존 정산 SQL, servedb 게시를 합한 시간이다.
- 단계별 중앙값을 각각 구해서 운반과 정산·게시의 합이 합계 중앙값과 조금 다르다.
- 모든 실행에서 랜딩 행 수가 원천과 일치했고, 기존 대사(`recon_result`, `recon_card`) 실패는 0건, 대상일 집계 합계는 마감 명세와 일치했다.
- 1,000만 주문은 측정하지 못했다. 100만 주문에서 Kafka 1,560MB, PostgreSQL 1,965MB를 썼으므로 비례하면 약 35GB가 필요하다. 측정 시점 Docker 디스크 여유는 약 22GB였다.

## CDC가 느린 이유

100만 주문을 1회 더 실행해 운반 구간을 나눴다. Debezium 로그의 테이블별 snapshot 완료 시각, 1초 간격의 컨슈머 랜딩 건수, 같은 Kafka 데이터를 새 컨슈머 그룹으로 다시 읽은 컨슈머 단독 처리량을 비교했다.

| 구간 | 시간 | Debezium → Kafka | 컨슈머 → 랜딩 | 느린 쪽 |
|---|---:|---|---|---|
| 결제 (270만 레코드) | 68.8초 | 55초, 초당 4.9만 | Debezium 완료 약 13초 후 완료 | Debezium |
| 주문 (310만 레코드) | 121.6초 | 58.7초, 초당 5.3만 | 초당 약 2.7만, Debezium 완료 약 63초 후 완료 | 컨슈머 |

1. 결제 단계는 Debezium snapshot이 느리다. 로그에 `Creating snapshot worker pool with 1 worker thread(s)`가 남아 있다. 한 스레드가 결제 원장 5개 테이블을 차례로 읽는다.
2. 주문 단계는 컨슈머가 느리다. 컨슈머 단독 재소비는 28개 파티션에서 초당 6.3만 레코드였다. 주문 단계는 데이터가 파티션 4개인 `order_item` 토픽에 몰려서 컨슈머 스레드 8개 중 4개만 일할 수 있다. 처리량이 절반인 것과 일치하지만, 스레드별 사용률은 직접 재지 않았다.
3. 커넥터마다 고정 지연이 있다. 주문 커넥터 등록 후 첫 10초는 초당 5,800레코드였다. 컨슈머가 패턴 구독으로 새 토픽을 찾는 주기(`metadata.max.age.ms`)가 10초다. 1만 주문에서도 운반이 18초 걸렸다.
4. 구조 비용이 있다. CDC는 테이블 전체를 레코드 단위로 Avro 직렬화·역직렬화하고 JSON 한 줄로 다시 쓴다. 파일 배치는 1만 행 묶음을 Parquet 열 단위로 쓴다.

검증하지 않은 개선 가설은 다음과 같다.

- Debezium snapshot을 병렬로 읽으면(`snapshot.max.threads`) 결제 단계가 줄어든다.
- `order_item` 토픽 파티션을 8개 이상으로 늘리면 주문 단계 컨슈머 처리량이 늘어난다.
- 스키마를 미리 등록해 커넥터를 동시에 등록하면 고정 지연을 한 번으로 줄인다.
- 세 가지가 모두 효과를 내도 Debezium 쓰기 속도(초당 약 5만)가 상한이다. 운반은 약 60초가 한계로 보이며, 파일 배치 추출 8.53초와 약 7배 차이가 남는다.

## 측정 방법

공통 준비는 다음과 같다.

1. 매 규모마다 전용 Compose 프로젝트를 새로 띄운다. 파일 배치는 `settlement-file-bench`, CDC는 `settlement-cdc-bench`를 쓴다. 기존 `settlement-*` 프로젝트와 볼륨을 공유하지 않는다.
2. DuckDB로 합성 데이터를 만들고 `COPY`로 결제·주문 DB에 적재한 뒤 `ANALYZE`한다. 이 준비 시간은 측정 결과에서 뺐다. 1,000만 주문의 적재는 233초였다.

파일 배치는 다음과 같이 잰다.

1. 실제 `export_bundle`과 `run` 함수를 그대로 호출한다. 제품 코드는 수정하지 않고 각 단계 함수를 시간 측정용 래퍼로 감쌌다.
2. dbt 시간은 dbt가 남긴 `run_results.json`의 `elapsed_time`을 쓴다. `compute_other`는 계산 단계 전체 시간에서 적재·검사·dbt 시간을 뺀 값이다.
3. 같은 bundle로 한 번 더 실행해 기존 run_id를 재사용하는지 확인한다. 재사용하지 않으면 측정을 실패로 끝낸다.

CDC는 다음과 같이 잰다.

1. 컨슈머를 먼저 띄우고 결제 → 주문 순서로 커넥터를 등록한다. 컨슈머 지표 `settlement_landed_records_total`이 원천 행 수에 도달한 시각까지를 운반 시간으로 잰다.
2. DLQ 지표가 0이 아니거나 300초 동안 랜딩 건수가 늘지 않으면 측정을 실패로 끝낸다.
3. 컨슈머를 정상 종료해 버퍼를 flush하고, 랜딩을 기존 `e2e_load.sql`로 적재한다. 적재 행 수가 원천과 다르면 실패로 끝낸다.
4. 기존 `03_settlement.sql`을 실행하고, 대사 실패와 대상일 합계를 확인한다.
5. 기존 `scripts/publish-serving.sh`와 같이 한 트랜잭션에서 `TRUNCATE` 후 `COPY`로 servedb에 게시한다.

## 한계와 다음 측정

- 파일 배치 추출 단계 안에서 무엇이 느린지는 나누어 재지 않았다. 원인 후보는 세 가지이며, 다음 측정에서 하나씩 확인한다.
  - 행을 Python 객체로 바꾼 뒤 Parquet으로 쓰는 변환 비용
  - 주문 상품을 1만 건씩 `order_no = ANY(...)`로 반복 조회하는 비용
  - 메모리 3.8GiB VM에서 기본 설정으로 띄운 PostgreSQL의 캐시 부족
- CDC는 1,000만 주문을 측정하지 못했다. Docker 디스크 한도를 늘린 뒤 같은 스크립트로 측정한다.
- CDC 운반 구간 분해는 1회 진단 결과다. 진단 스크립트는 저장소에 포함하지 않았다.
- CDC를 하루 동안 나눠 운반하는 운영 방식의 마감 후 지연은 측정하지 않았다. 위 표의 CDC 값은 컨슈머가 밀리지 않는다는 가정이다.
- Python 프로세스의 최대 메모리는 보고하지 않았다. 같은 프로세스에서 합성 데이터 생성과 적재도 해서 배치만의 사용량을 분리할 수 없다.
- 여러 날짜를 동시에 실행하는 경우, PostgreSQL을 별도 서버에 둔 경우, DuckDB 스레드를 늘린 경우는 측정하지 않았다.
- [기존 성능 실험](BENCHMARK.md)은 다른 머신(메모리 31.5GiB)에서 기존 SQL 정산만 잰 결과다. 측정 범위가 달라서 이 문서의 수치와 직접 비교하지 않는다.

## 재현

```bash
# Docker와 .venv-file-batch가 필요하다. 값은 생성할 전체 주문 수다.
bash bench/file-batch-bench.sh "100000 1000000 10000000"

# CDC는 빌드된 normalize bootJar와 비어 있는 호스트 포트 55440~55444가 추가로 필요하다.
(cd normalize && ./gradlew --gradle-user-home ../.gradle-file-batch bootJar --no-daemon)
bash bench/cdc-bench.sh "100000 1000000"
```

- 결과는 `data/file-batch/bench/<시각>/orders=<N>/report.json`과 `data/file-batch/bench-cdc/<시각>/orders=<N>/report.json`에 남는다. `data/`는 Git에 포함하지 않는다.
- 파일 배치 1,000만 주문 1회에 약 7분 20초가 걸리고, 실행 후 `data/`에 bundle·실행 산출물이 약 4.7GB 남는다.
- CDC 100만 주문 1회에 약 4분이 걸리고, 실행 후 `data/`에 랜딩 약 711MB가 남는다.
- `BENCH_DAYS`로 결제를 분산할 일수를 바꾼다. 파일 배치는 `BENCH_PG_PORT`로 호스트 포트(기본 `55450`)를 바꾼다.
- 파일 배치의 PostgreSQL 비밀번호는 실행마다 새로 만들고 출력하지 않는다. CDC는 `compose.cdc-test.yml`이 고정한 로컬 전용 테스트 계정을 쓴다.
- 두 스크립트 모두 끝나면 벤치 전용 컨테이너와 볼륨을 지운다.
